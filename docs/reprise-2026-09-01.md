## Le projet

APP CHOPIN — application métier Next.js 14 (App Router, TypeScript strict) + Supabase,
pour SCEA Chopin Conditionnement. Cycle complet : offre → négociation multi-tours →
commande → préparation atelier et palette → livraison → facture → règlement → relance.
20 pages, 8 modules d'actions serveur, 21 migrations, ~14 500 lignes.
Voir `CLAUDE.md` et `docs/plan.md`.

Projet Supabase : ref **`aebtpaipekivqwljrxet`** (eu-central-1, Postgres 17.6).
C'est une base **réellement utilisée** : 12 comptes, 3 entreprises, 6 offres,
5 commandes, 3 factures numérotées, 1 règlement, 48 notifications. Ne détruis rien.

## Règles absolues

1. **Ne lance jamais `npm run build` pendant que `npm run dev` tourne.** Ils partagent
   `.next` et le serveur finit cassé, avec des pages introuvables. Arrête le dev,
   compile, relance.

2. **N'utilise jamais `supabase db push`.** L'historique distant a été écrit via MCP :
   les versions distantes des migrations 13 à 18 sont des horodatages
   (`20260618103834`, `20260728094623`…) qui ne correspondent pas aux noms de fichiers
   locaux (`00013_…`, `00018_…`). `db push` croirait ces six migrations non appliquées
   et les rejouerait sur la production. Applique 00019 et 00020 une par une, explicitement.

3. **Ne touche pas à `.env.local`.** Si une clé manque, dis-le-moi ; ne l'invente pas,
   ne la contourne pas.

4. **Pas de `any`, pas de `@ts-ignore`.** TypeScript strict est la règle du projet.

5. **Ne commit jamais de `node_modules`.** C'est un piège réel ici, voir l'étape 1.

## Étape 2 — appliquer les migrations 00019 et 00020

Elles sont écrites, relues et sûres : idempotentes (`IF NOT EXISTS`, `CREATE OR REPLACE`,
`DROP POLICY` avant recréation), aucun `DROP TABLE`, aucune donnée touchée. Tant qu'elles
ne sont pas passées, les pages `/atelier` et `/transporteurs` échouent au chargement —
le code interroge des tables que la base ne connaît pas.

**Elles doivent partir en deux exécutions séparées.** `00019` ne fait qu'ajouter la
valeur d'enum `responsable_conditionnement` ; PostgreSQL interdit d'utiliser une valeur
d'enum dans la transaction qui la crée, et `00020` s'en sert. Applique 00019, attends
qu'elle soit validée, puis 00020.

Moyens, par ordre de préférence :

1. le serveur MCP Supabase s'il est configuré → `apply_migration`, un appel par fichier,
   en les nommant `00019_role_responsable_conditionnement` et `00020_logistique_atelier` ;
2. sinon `psql` avec la connection string du projet ;
3. sinon dis-le-moi : je les collerai dans l'éditeur SQL, mais alors prépare-moi les
   deux blocs prêts à coller.

Ce que `00020` installe, et donc ce qu'il faut vérifier ensuite en base :

- la table `carriers` et ses policies RLS
- sur `orders` : transporteur, lieux d'enlèvement et de livraison, poids, épinglage
- sur `pallet_sheets` : type de palette, colis, cerclage, `bl_number`
- la fonction `generate_bl_number()`
- la vue `orders_for_conditionnement` (celle qui masque les prix à l'atelier)
- l'enum `user_role` à six valeurs

## Étape 3 — générer les types de la base

C'est le vrai chantier caché du projet, et il conditionne tout le reste.

`types/database.ts` fait **14 lignes** : c'est le fichier d'amorçage de juin, jamais
remplacé. Il déclare `Tables: Record<string, never>` et un enum de rôles arrêté à cinq
valeurs. Autrement dit le client Supabase ne connaît **aucune** table du projet : toutes
les requêtes de l'application sont non typées, et les **35 conversions forcées**
(`as any`, `as unknown as`) présentes dans le code servent à masquer ce trou. C'est ce
qui avait laissé passer le bug de numérotation des factures — un appel à une fonction
RPC inexistante que personne ne voyait.

La cause est bête : le script est cassé depuis le premier jour.

```json
"types:supabase": "supabase gen types typescript --local > types/database.ts"
```

`--local` vise une stack Supabase locale qui ne tourne pas ici — il n'y a même pas de
`supabase/config.toml`, le projet n'est pas lié. La commande a donc toujours échoué.
Corrige-la en visant le projet distant :

```json
"types:supabase": "supabase gen types typescript --project-id aebtpaipekivqwljrxet > types/database.ts"
```

Puis lance-la. Il faut être authentifié (`npx supabase login`, ou un `SUPABASE_ACCESS_TOKEN`
dans l'environnement) — si tu n'as pas d'accès, dis-le-moi plutôt que de bricoler.

À faire **après** l'étape 2, pour que les types générés contiennent `carriers`, les
colonnes logistiques, `generate_bl_number` et le sixième rôle.

## Étape 4 — laisser TypeScript parler

Arrête le serveur de dev, puis `npm run build`. Avec de vrais types pour la première
fois, il va sortir beaucoup d'erreurs d'un coup. C'est normal et c'est le but.

Traite-les ainsi :

- **retire les casts devenus inutiles** — supprimer ces 35 conversions forcées est
  l'objectif de l'opération, pas un effet de bord ;
- **quand une erreur révèle un vrai bug** (mauvais nom de colonne, fonction RPC
  inexistante, champ nullable mal géré, statut absent de l'enum), signale-le-moi
  explicitement au lieu de le faire taire par un cast ;
- n'ajoute aucun `any` nouveau, aucun `@ts-ignore`.

Point de fin d'étape : combien d'erreurs au départ, combien de casts supprimés, quels
vrais bugs découverts. Commit séparé, message explicite.
